# Android 1.0 background override enumeration: native findings (2026-10-31)

## Evidence source
- Android 1.0 APK: release `XR1/base.apk`.
- Native disassembly generated by GitHub Actions run 41197680150 (override iterator, hash helper and Spine ID getter) and run 41197785286 (ResolveOverride).
- IL2CPP dump: `azurearchive-ios-il2cpp-comparison` artifact, Android ARM64 `dump.cs`.
- These are Android ARM64 findings. No Android address or instruction is reused in iOS code.

## Confirmed override container fields
`ResourceOverrideData` exposes:
- `BgOverrides`: `HashSet<string>`, backing field offset 0x30.
- `BgSpineOverrides`: `List<BgSpineOverrideData>`, backing field offset 0x40.
- `basePath`: string field offset 0x50.

The `BackgroundResource.Overrides(data, source)` iterator receives the selected local/global ResourceType and iterates both collections. The iterator's generated body is complex; image construction is described below, while Spine descriptor construction remains under review.

## Image override projection
Native disassembly of `BackgroundResource.<Overrides>d__29.MoveNext` at RVA 0x34332F0 shows the image-path branch:
1. Read an entry from `BgOverrides`.
2. Replace backslash (0x5c) with slash (0x2f).
3. Call `Path.GetFileNameWithoutExtension` to obtain the resource name.
4. Call `Util.CalculateHash(name)` for the resource ID.
5. Construct a `BackgroundResource` with Image kind (enum value 1), the supplied source, normalized relative path, `basePath` root, and null Spine data.

This is implemented in `BackgroundImageOverrideFactory.Create`. It preserves the source argument and uses the existing `BackgroundResourceDescriptor` and `SafeResourcePath` rather than creating another loader.

## Spine ID
`ResourceOverrideData.BgSpineOverrideData.get_Id` at RVA 0x325BB9C loads the `Identifier` field (offset 0x10) and tail-branches to `Util.CalculateHash` at RVA 0x32E1430. This confirms that Spine override IDs are derived from Identifier. It does not yet establish the complete Spine descriptor's Name/Path/Root mapping or its filtering behavior.

## Hash implementation boundary
The Android `Util.CalculateHash(string)` native body uses a byte-encoding path and then the game's `xxHash.CalculateHash(Stream, len=-1, seed=0)` routine. The xxHash32 constants are present in the recovered dump:
- 2654435761, 2246822519, 3266489917, 668265263, 374761393.

`BackgroundResourceIdHash` currently ports the ordinary short-string case as UTF-8 bytes + xxHash32 seed 0. It returns 0 for null and rejects strings longer than 256 UTF-16 code units because the native method has a separate long-string branch. Standard xxHash vectors are tested. The exact encoding field identity and long-string branch still need differential verification against the Android implementation before calling this a byte-for-byte equivalent.

## ResolveOverride predicate caveat
`BackgroundResource.ResolveOverride` at RVA 0x3432DFC calls `Overrides(local, 2)`, then `Overrides(global, 1)`, and uses FirstOrDefault for each before returning. The local predicate at RVA 0x3433298 directly compares the candidate BackgroundResource ID with the captured requested ID. The symbol-labeled global predicate target at RVA 0x34332BC does not disassemble as an equivalent ID comparison; do not assume its exact filter/null behavior is proven. The portable resolver currently applies the ID predicate to both sequences as a candidate mirror; global predicate semantics remain an explicit verification item.
